# GO — инициализация рабочей сессии

Задача от пользователя: $ARGUMENTS

## Фаза 1: Состояние сессии

Проверь `NEXT_SESSION.md` в корне проекта:
- Если файл содержит план — сообщи пользователю и спроси: продолжить по плану или начать новую задачу
- Если файл пуст или отсутствует — переходи к фазе 2

## Фаза 2: Сбор контекста проекта

### 2.1 Определение области задачи

На основе задачи пользователя определи, какие модули затронуты:

| Область | Модули |
|---------|--------|
| Фича: приём запросов, бизнес-логика, схемы | `backend/app/<feature>/` — `<feature>_handler.py`, `services/`, `schemas/` |
| Общее для нескольких фич | `backend/app/dependencies.py`, `constants.py`, `schemas/`, `services/`, `utils/` |
| Общие модули проекта | см. `backend/devtools/CLAUDE.md` |
| ORM модели, таблицы | `backend/app/database/models/` |
| Перечисления | `backend/app/database/enums/` |
| Redis операции | `backend/app/redis/`, если Redis есть в проекте |
| Конфиг, переменные окружения | `backend/app/config.py` |
| Миграции | `backend/migrations/` |
| Тесты | `backend/tests/unit/`, `integration/`, `live/` |

### 2.2 Чтение затронутых файлов

Читай только файлы, реально затронутые задачей. Не читай весь проект вслепую.

## Фаза 3: Загрузка документации

Обязательно прочитай релевантные доки. Не работать по памяти.

| Условие | Документ |
|---------|----------|
| Любая задача | `CLAUDE.md` — структура, стек, env-переменные, ТЗ; к нему подключены общий кодстайл, `backend/devtools/CLAUDE.md` и `user_role.md` |
| Задача по ТЗ | Файлы из раздела «ТЗ и материалы» корневого `CLAUDE.md` |

## Фаза 4: Контрольные ограничения

Перед планированием держи в голове железные правила:

### Код стайл
- Type hints везде
- Один файл = одна ответственность
- Фичи не импортируют друг друга; общее для нескольких фич — в корне `app/`
- Схемы и структуры данных — в `schemas/` своего модуля
- Ошибки сервисов — классы из `app/utils/service_errors.py`, в хендлерах нет try/except
- Комментарии отглагольными существительными, шапка файла, комментарий над каждым классом и методом
- Импорты: stdlib → third-party → internal, без `import *` и без импортов внутри функций
- Никакого капслока, разделителей-линий (`# ======`), magic numbers и ссылок на ТЗ в комментариях
- Бизнес-логика только в `services/`, хендлеры — только слой API

### Инфраструктура
- Не ставить пакеты локально — только через `requirements.txt` + Docker
- Все новые зависимости добавлять в `requirements.txt` с точной версией
- Запуск `./start.sh`, тесты `./run_tests.sh`, линт `./lint.sh` — из корня проекта

### Обязательный алгоритм работы
- доки → требования → план → подтверждение → код

## Фаза 5: Планирование

1. Составь пошаговый план реализации
2. Для каждого шага укажи: что делаешь, какие файлы трогаешь, какие риски
3. Покажи план пользователю
4. Дождись подтверждения
5. Не пиши код, пока план не утверждён

## Фаза 6: Выполнение (после утверждения)

1. Запиши утверждённый план в `NEXT_SESSION.md`
2. Выполняй задачу по плану, шаг за шагом
3. После каждого логического блока проверяй, что ничего не сломал (читай зависимые файлы)
4. Прогони `./lint.sh` и `./run_tests.sh`
5. Очисти `NEXT_SESSION.md` после завершения

> `NEXT_SESSION.md` никогда не коммитить в git.
