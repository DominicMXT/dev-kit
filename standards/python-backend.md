# Бэкенд на Python — код-стайл, архитектура, структура папок и нейминг

Общие правила для всех бэкендов на FastAPI. Подключаются в корневом `CLAUDE.md` проекта.
Правила конкретного проекта — его общие модули, доменные имена, особенности тестов — в `backend/devtools/CLAUDE.md`.

## Модульная архитектура

- Один файл = одна ответственность
- Один модуль = один домен
- Нет циклических импортов
- Однонаправленные зависимости: `handler` → `services/` → `models/`
- `services/` никогда не импортируют из хендлеров
- Фичи не импортируют друг друга: всё, что нужно двум и более фичам, лежит в корне `app/`
- Общие модули (`app/schemas/`, `app/services/`, `app/utils/` и общие пакеты проекта) не импортируют фичи
- Redis — только через `app/redis/`
- Конфиг — только через `app/config.py` (Pydantic Settings)

### Вертикальные слайсы

Каждый домен — отдельный пакет, глобальных `app/handlers/` нет:

```
app/<feature>/
  <feature>_handler.py   # APIRouter: приём запроса → вызов сервиса → ответ
  schemas/               # Схемы запросов, ответов и структуры данных фичи
  services/              # Бизнес-логика домена
```

- Роутер фичи подключается в `app/main.py`
- Правила слоёв действуют внутри слайса: handler → services → models
- В корневых `app/services/` и `app/schemas/` — только то, что нужно двум и более фичам

## Структура папок

```
<проект>/
  start.sh                             # Сборка без кеша и запуск dev-стека с миграциями
  run_tests.sh                         # Тесты в Docker с отчётом
  lint.sh                              # ruff check + ruff format по backend/
  docker/                              # Dockerfile и compose-файлы: dev, prod, test
  docs/                                # ТЗ и материалы
  backend/
    app/
      main.py                          # Сборка приложения: lifespan, middleware, ответы на ошибки сервисов, роутеры
      config.py                        # Pydantic Settings: все env-переменные
      constants.py                     # Константы, общие для нескольких фич и модулей
      dependencies.py                  # FastAPI-зависимости, общие для нескольких фич
      schemas/<назначение>_schemas.py  # Схемы, общие для нескольких фич
      services/<назначение>_service.py # Сервисы, общие для нескольких фич
      utils/<назначение>.py            # Утилиты без доменных зависимостей, базовые ошибки сервисов
      redis/<назначение>.py            # Операции с Redis, если он есть в проекте
      database/
        initialization.py              # TORTOISE_ORM, init_db(), close_db()
        models/<сущность>.py           # Одна модель — один файл
        enums/<домен>.py               # Enum-типы домена
      <модуль>/                        # Общий модуль нескольких фич: расчёты, клиент внешнего API
        <назначение>.py
        schemas/<назначение>_schemas.py
        constants.py
      <feature>/
        <feature>_handler.py           # APIRouter фичи
        <назначение>.py                # Точка входа из командной строки (python -m), если нужна
        dependencies.py                # FastAPI-зависимости фичи, если нужны
        constants.py                   # Константы фичи, если нужны
        schemas/<feature>_schemas.py   # Схемы и структуры данных фичи
        services/<feature>_service.py  # Основная бизнес-логика фичи
        services/<назначение>_service.py # Дополнительные сервисы фичи
        utils/<назначение>.py          # Утилиты, нужные только этой фиче
      <group>/                         # Группа связанных фич
        <feature>/                     # Слайсы группы по той же схеме
        shared/                        # Общее только для фич группы
    migrations/models/                 # Миграции Aerich
    tests/
      conftest.py                      # Хук русских имён тестов и общие фикстуры
      helpers.py                       # Общие данные и помощники тестов
      unit/                            # Логика и схемы без БД
      integration/                     # Хендлеры и сервисы на настоящей PostgreSQL
      live/                            # Прогоны против настоящих внешних API
    devtools/                          # CLAUDE.md проекта и user_role.md, в git не попадают
    pyproject.toml                     # Конфиг ruff, pytest, coverage и aerich
    requirements.txt                   # Зависимости приложения
    requirements-dev.txt               # Зависимости тестов
    .env.example                       # Шаблон переменных окружения
```

**Модульность:**
- Всё, что нужно одной фиче, лежит внутри её пакета: схемы, сервисы, утилиты, зависимости, константы
- Нужное двум и более фичам — в корне `app/`: `schemas/`, `services/`, `utils/`, `dependencies.py`, `constants.py`;
  крупный общий домен (расчёты, клиент внешнего API) — отдельным модулем в корне `app/`
- Общее только для группы фич — в `<group>/shared/`, а не в корне
- Структуры данных (Pydantic-схемы и dataclass) — в `schemas/` своего модуля; в файлах логики — функции,
  исключения и классы с поведением (клиенты, лимитеры, middleware)

## Нейминг

**Папки и файлы:**
- Папки и файлы — `snake_case`
- Файлы слайса начинаются с имени фичи: `<feature>_handler.py`, `schemas/<feature>_schemas.py`, `services/<feature>_service.py`
- Дополнительные файлы — по назначению: `<что>_service.py`, `<система>_client.py`, `<что>_builder.py`
- Схемы общих модулей — по назначению: `schemas/event_schemas.py`, `money/schemas/purchase_plan_schemas.py`
- Модель — сущность в единственном числе (`purchase.py` → класс `Purchase`), таблица — во множественном (`Meta.table = "purchases"`)
- Enum-ы — файл по домену (`enums/purchase.py`), экспорт — через `enums/__init__.py` и `__all__`
- Тесты — `test_<модуль>_<что>.py`: в unit суффиксы `_pure` (чистая логика) и `_schemas` (схемы), в integration — `_handler` и `_service`

**Код:**
- Функции и переменные: `snake_case`
- Классы: `PascalCase`
- Константы: `UPPER_CASE`
- Приватные функции и переменные: `_snake_case`
- Роутер фичи — `router = APIRouter(prefix="/api/<ресурс>", tags=["<ресурс>"])`
- Имена простые и понятные любому бэкендеру без пояснений: `job_id`, а не абстрактный «ключ идемпотентности»
- Функция с записью в журнал или другим побочным действием называет его: `show_today`, `record_event`, а не `today_view`
- Доменные имена — по словарю из ТЗ проекта

## Чистота кода

**Функции:**
- Одна функция = одна задача
- Никаких side effects без явного указания в названии
- Никаких magic numbers и magic strings — только enums или константы
- Никаких функций внутри функций — только на уровне модуля

**Типизация:**
- Type hints обязательны везде: параметры функций и возвращаемые значения

**DRY:**
- Никакого дублирования логики
- Общая логика выносится в `services/` или `utils/`: внутри фичи — в её папки, для нескольких фич — в корень `app/`

**Ошибки сервисов:**
- Ошибка сервиса наследует `NotFoundError`, `ConflictError`, `TooLargeError` или `UnprocessableError` из `app/utils/service_errors.py`
  и несёт текст для человека в `detail`
- Статус ответа задаётся по базовому классу в `app/utils/http_errors.py` (404, 409, 413, 422); в хендлерах нет try/except
- 401 и 403 — `HTTPException` в `app/dependencies.py`

**База данных:**
- Запросы через Tortoise ORM (`filter` / `annotate` / `group_by` / `values`), а не сырой SQL через `execute_query_dict`
- Индексы — под реальные запросы: уникальные, составные, частичные; частичный уникальный индекс Tortoise не объявляет —
  он пишется SQL-ем в миграции Aerich

## Импорты

- Порядок: stdlib → third-party → internal
- Никаких `import *`
- Никаких импортов внутри тел функций (ruff `PLC0415`); позднее связывание — через модуль и `module.attr`

## Язык

- Комментарии, docstring и логи — на русском
- Имена в коде — на английском

## Стиль комментариев

**Комментарии пишутся отглагольными существительными с заглавной буквы:**
- Правильно: "Создание пользователя", "Проверка токена", "Получение статистики"
- Неправильно: "Создаём пользователя", "Проверяем токен", "CREATE USER"

**Обязательные элементы в каждом файле:**
1. Шапка файла — docstring в начале с описанием модуля
2. Комментарий над каждым классом (`# Описание класса`), включая `class Meta` моделей
3. Комментарий над каждой функцией/методом (`# Описание функции`)
4. Inline комментарии перед каждым логическим блоком внутри функции

**Запреты:**
- Никакого капслока ("ВАЖНО", "ВНИМАНИЕ", "TODO: FIX THIS"); заглавными пишется только название модуля в шапке файла
- Никаких разделителей посреди кода (`# ==================`)
- Разделители допустимы только в шапке файла
- Никаких слов "важно", "критично", "обратите внимание"
- Никаких глаголов ("создаём", "проверяем", "возвращаем")
- Никаких ссылок на ТЗ, задачи, случаи, релизы и прототип: комментарий описывает, что делает код
- Никаких обоснований «почему так сделано» для проверяющего — только что делает код

**Формат шапки файла:**
```python
"""
===========================================================================
 НАЗВАНИЕ МОДУЛЯ - КРАТКОЕ ОПИСАНИЕ
===========================================================================

Описание назначения модуля.

Содержимое:
- Что содержит модуль

Бизнес-логика:
- Ключевые правила и флоу
"""
```

- В названии — тип и имя модуля (`PURCHASES HANDLER`, `МОДЕЛЬ USER`), после тире — русское описание содержимого, а не технология
- У файлов общих модулей — префикс модуля: `UTILS MASKING`, `MONEY PURCHASE PLAN`, `LLM COACH`
- Шапка описывает, что делает модуль, а не где он лежит: не `APP CONFIG`, а `КОНФИГУРАЦИЯ ПРИЛОЖЕНИЯ`
- В «Содержимое» — все публичные функции, классы и константы модуля
- Шапки не удаляются и не сокращаются при чистке кода

**Формат docstring функции:**
```python
async def get_user(user_id: int) -> User:
    """
    Получение пользователя по идентификатору.

    Бизнес-логика:
    1. Проверка существования -> загрузка из БД

    Args:
        user_id: Идентификатор пользователя

    Returns:
        Объект пользователя

    Raises:
        UserNotFoundError: Пользователь не найден
    """
```

**`__init__.py`:**
- С экспортами — однострочный docstring `"""Экспорт ..."""` и `__all__`
- Без экспортов — полностью пустой файл, без шапки

**Файлы** заканчиваются переводом строки.

## Слои приложения

| Слой | Путь | Ответственность |
|------|------|-----------------|
| Хендлеры | `app/<feature>/<feature>_handler.py` | Приём запросов, вызов services, отправка ответа |
| Сервисы | `app/<feature>/services/` | Вся бизнес-логика фичи |
| Схемы | `app/<feature>/schemas/` | Схемы запросов и ответов и структуры данных фичи |
| Общие зависимости | `app/dependencies.py` | FastAPI-зависимости нескольких фич |
| Общие сервисы | `app/services/` | Логика, нужная двум и более фичам |
| Общие схемы | `app/schemas/` | Схемы, нужные двум и более фичам |
| Модели | `app/database/models/` | ORM-схемы таблиц, без логики |
| Перечисления | `app/database/enums/` | Enum-типы моделей, API и конфига |
| Redis | `app/redis/` | Все операции с Redis, если он есть в проекте |
| Конфиг | `app/config.py` | Все env-переменные |
| Утилиты | `app/utils/` | Вспомогательные функции без зависимостей от домена, базовые ошибки сервисов |

## Инфраструктура

- Не ставить пакеты локально и не создавать venv — только через `requirements.txt` + Docker (Python 3.12)
- Зависимости приложения — в `requirements.txt`, тестовые — в `requirements-dev.txt`; точная версия (`==`), без диапазонов
- Docker — в папке `docker/`: `Dockerfile` (prod), `Dockerfile.dev` (исходники из volume, автоперезапуск uvicorn), `Dockerfile.test`;
  `docker-compose.yml` (dev), `docker-compose.prod.yml`, `docker-compose.test.yml`; контекст сборки — `backend/`, там же `.dockerignore`
- Скрипты — в корне проекта:
  - `./start.sh` — сборка образов без кеша, пересоздание контейнеров, миграции
  - `./run_tests.sh` — тесты в Docker с коробочным отчётом
  - `./lint.sh` — ruff check + ruff format по `backend/`
- Секреты — только в `backend/.env` (в git не попадает), шаблон — `backend/.env.example`
- Служебные файлы разработки (`CLAUDE.md`, `backend/devtools/`) — в `.gitignore`;
  `.serena/`, `.claude/`, `NEXT_SESSION.md`, `.copier-answers.yml` — в `.git/info/exclude`
- Конфиг ruff в `pyproject.toml`: `line-length = 150`,
  `select = ["E", "F", "W", "I", "B", "UP", "RUF", "T201", "PLC0415"]`,
  `ignore = ["E501", "RUF001", "RUF002", "RUF003", "RUF012", "B008"]`, isort `known-first-party = ["app"]`
  - `T201` запрещает `print()`, `PLC0415` — импорты внутри функций
  - `B008` отключён под FastAPI `Depends(...)` в дефолтах аргументов

## Async

- Нет блокирующих операций в async контексте (синхронные I/O, `time.sleep`)
- `await` расставлен корректно — нет забытых coroutines
- Нет race conditions при параллельных запросах

## Безопасность

- Нет SQL injection (Tortoise ORM, параметризованные запросы)
- Нет command injection
- Валидация входных данных от пользователя
- Нет `print()` в продакшн-коде — только logging
- Токены и секреты только в env-переменных, не в коде

## Тестирование

- `tests/unit/` — логика и схемы без БД; `tests/integration/` — хендлеры и сервисы на настоящей PostgreSQL (и Redis, если он есть);
  `tests/live/` — прогоны против настоящих внешних API, в обычный прогон не входят (`addopts = "-m 'not live'"`)
- Тесты проверяют реальную работу: где есть БД — интеграционный тест на настоящей PostgreSQL, а не мок;
  внешние HTTP-сервисы — локальные ASGI-серверы через `httpx.ASGITransport`, а не `MockTransport`
- Защиту от гонок и дублей подтверждает только тест одновременных запросов (`asyncio.gather` + `asyncio.Barrier`),
  который падает на старом коде; правило держит PostgreSQL — уникальное ограничение или `pg_advisory_xact_lock`
- Маркеры `unit` / `integration` / `live` — через `pytestmark = pytest.mark.<маркер>` в модуле; `asyncio_mode = "auto"`
- Имя теста — однострочный русский комментарий над `def` отглагольным существительным (хук в `conftest.py`)
- Шапка обязательна и в файлах тестов
- Общие фикстуры — в `conftest.py`; общие данные и помощники — в `tests/helpers.py`;
  БД — чистая схема на каждый тест, Redis — `flushdb` до и после теста
- Параметры и ключи живых прогонов — только из env, в коде тестов их нет
- Покрытие `app` — 100% (`fail_under = 100`); исключены `app/config.py`, `app/main.py`, `app/database/initialization.py`;
  нетестируемые ветки помечаются `# pragma: no cover`
- Код не подгоняется под тесты, а тесты — под код
- Запуск только через Docker: `./run_tests.sh` из корня проекта (в неинтерактивном режиме — `echo n | ./run_tests.sh`)

## Порядок работы перед написанием кода

1. Прочитать память проекта (`MEMORY.md` + релевантные файлы памяти)
2. Прочитать `CLAUDE.md` проекта — к нему подключены эти правила, `backend/devtools/CLAUDE.md` и `user_role.md`
3. Прочитать ТЗ задачи — файлы из раздела «ТЗ и материалы» корневого `CLAUDE.md`
4. Прочитать релевантные файлы проекта и документацию используемых библиотек
5. Составить план и показать пользователю
6. Дождаться подтверждения
7. Только потом писать код
8. Перед сдачей — `./lint.sh` и `./run_tests.sh` без ошибок
